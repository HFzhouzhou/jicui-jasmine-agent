# 微信小程序点单衔接方案

核验日期：2026-10-09。本文是接入方案，不代表已经接通品牌小程序或取得其开发权限。

## 产品目标与边界

形成「AI 推荐 → 用户调整并确认茶单 → 用户点击前往官方小程序 → 官方小程序核验并展示配置 → 用户自行下单和支付」的流程。用户可以取消跳转、继续调整或重新选店。

打开小程序与还原商品配置是两项不同能力。微信的链接可以传递页面参数，但不会自动替第三方小程序选择商品、修改购物车或创建订单。完整的配置衔接需要品牌小程序已经支持相应参数协议，或由品牌开发方新增承接页面。

本项目不自动下单、不代用户支付。AI 茶单始终是参考与待确认信息；最终商品可售状态、规格、库存、价格和优惠以用户选定门店的官方小程序确认为准。

## 第一期：可以独立完成的功能

- 保存小程序中取得的官方产品资料与宣传素材，记录来源、采集日期、门店和适用范围。宣传图上的价格不直接当作所有门店的实时售价。
- 建立饮品名称与官方商品信息的对应关系。未查证的配料、过敏原、咖啡因和可选规格继续保持未知，不从图片或品名推断为已确认事实。
- 提供「点单摘要」，展示已确认的饮品、数量、杯型、甜度、冰量、加料和参考价格。只允许选择已核实的规格；未确定的项目清楚标注。
- 支持复制或展示摘要，让用户在官方小程序中核对并完成选择。摘要不应称为已提交订单。
- 只有拿到并验证可用的官方链接或小程序码后，才提供对应的「打开官方小程序」入口。未实现参数承接时明确说明需要在小程序中重新选择商品与规格。

没有真实可用入口时，不展示会误导用户的「一键下单」「配置已同步」或假跳转按钮。不把静态二维码跳转描述为已带入配置。

## 第二期：品牌接入后的配置承接

建议双方使用短期茶单标识（`draftToken`）传递已确认的选择，而不是在跳转地址中塞入完整订单。

1. 用户确认茶单并主动点击前往官方小程序。
2. 我方服务端生成短期、不可猜测的茶单标识，保存已确认的商品、规格、数量、门店和数据版本；不在链接中包含手机号、地址或支付信息。
3. 品牌认可的链接或小程序码携带该标识，打开约定的正式承接页面。页面路径及字段名须由双方确认，不能自行猜测现有小程序的内部路径。
4. 品牌服务端读取并校验茶单，按官方商品与规格 ID 映射配置，重新检查门店、可售状态、库存、规格组合和实时价格。已过期、售罄、规格变更或价格变化时，向用户展示明确结果并允许调整。
5. 品牌小程序展示最终配置，用户核对后自行下单、支付。只有收到真实业务结果，才能标记相应状态；跳转成功不等于下单成功或支付成功。

短期标识的有效期、读取权限、重复打开行为、失效提示和数据保留时间由双方约定。茶单修改后应使用新的版本，避免旧链接带入过时配置。上述方案是建议的业务协议，并非微信自带的通用购物车接口。

### 需要品牌提供或确认

- 正式小程序 AppID，以及可承接配置的页面路径与参数协议。
- 小程序开发方或点单系统服务商的对接人；现有系统是否支持商品深链、规格参数或外部茶单接收。
- 门店、商品、规格、加料的官方 ID 和合法组合，及可售状态、库存、价格的校验方式。
- 生成并维护跳转链接的方式：品牌服务端提供，或在正规授权后由接入方服务端调用。无需为单纯跳转把品牌 AppSecret 暴露给网页。
- 官方商品图片、宣传图等素材的原始文件与可使用范围。

## 门店商品与规格的实时同步契约

门店售罄、价格、甜度、冰量及加料可选项可以通过品牌或其点单系统提供的接口同步。**目前尚未确认品牌已开放这些接口，也未取得商家接入授权。** 以下是待双方确认的接口契约，不是现有能力声明。截图和人工采集资料只代表采集当时的情况，不能称为实时库存或实时规格。

### 最小数据与接口范围

| 数据 | 建议约定的内容 |
| --- | --- |
| 门店 | 稳定的门店 ID、名称、营业状态，以及适用的自取或配送方式。 |
| 商品 | 稳定的商品 ID、名称、所属门店或可售门店范围、上架状态、图片及说明。品牌统一资料与门店差异分别保存。 |
| SKU 与选项 | SKU ID、杯型、甜度、冰量、加料的选项 ID、默认值、必选规则、合法组合及门店当前是否可选。不能把一家店的选项复制为全品牌通用规则。 |
| 价格与可售状态 | 门店与 SKU 对应的价格、加料价、售罄状态；如品牌只开放是否可售，不将其推断为具体库存数量。优惠与最终应付价在官方结算时确认。 |
| 变更标识 | `updatedAt` 或单调递增的 `version`，删除/下架标识，以及分页或增量游标。明确时间与版本的含义，避免把我方抓取时间误当成品牌更新时间。 |
| 配置校验 | 在指定门店校验商品、规格组合、数量、库存与价格的接口；返回有效配置、失效原因及必要的替代选项。 |

双方还需约定鉴权方式、授权门店范围、调用频率、错误格式和接口版本。商家授权凭证、访问令牌与签名密钥仅保存在服务端，不交给浏览器或模型，不写入日志或仓库。读取商品目录的权限与创建订单的权限分别管理；本方案不要求我方取得代用户支付能力。

### 同步与一致性

- 优先使用品牌支持的变更通知（Webhook），收到事件后按契约验签、去重，并根据商品或门店 ID 拉取最新状态。不能假设通知一定按顺序到达或永不丢失。
- 品牌没有变更通知时，使用带 `updatedAt`、`version` 或游标的增量轮询；同步间隔遵守其限流与服务约定。必要时定期全量对账，处理漏失的下架或删除事件。
- 保存品牌数据版本、品牌更新时间和我方最近一次成功同步时间；按版本拒绝旧事件覆盖新状态。接口不提供版本时，与品牌另行约定可用的一致性判断方式。
- AI 推荐前按用户选择的门店读取当前资料；用户更换门店后重新校验已选商品和选项。切换门店不能沿用上一门店的可售结论。
- 创建跳转茶单前重新校验配置；品牌小程序承接后、用户提交订单前再次校验。同步结果只是快照，不能保证用户支付前库存保持不变。

### 接口失败与尚未接入时

- 短暂故障时可以展示最近一次成功同步的缓存，但同时说明「最近更新于……，当前可售情况待确认」。不得把过期缓存标为实时可售，也不能静默把无法校验的配置当作已确认订单。
- 无法完成最终校验时保留点单摘要，引导用户到官方小程序核对；不能显示「配置已同步」或「库存已锁定」。价格或选项发生变化时列出变化，交由用户重新确认。
- 接口接通前，可先通过人工后台维护已核实的商品、规格、价格与售罄状态，记录来源、核验门店和更新时间。人工维护与截图采集明确标为人工资料，不宣称自动实时同步。
- 联调至少覆盖门店差异、甜度选项取消、售罄后恢复、价格变化、商品下架、重复/乱序事件、同步中断与恢复，以及用户提交前状态再次变化。

## 不同访问环境

| 环境 | 建议方式 | 接入条件与处理 |
| --- | --- | --- |
| 手机普通浏览器 | 优先使用 URL Link | 微信官方支持网页等入口；安卓或微信内访问可能先经过官方 H5 中间页。生成能力与目标品牌小程序相关。保留取消、失败和返回调整的入口。 |
| 微信内网页 | URL Link；后续可优化为 `wx-open-launch-weapp` | 开放标签需要认证服务号的安全域名与签名配置，或符合条件的小程序云开发静态托管。由用户点击触发。我们的独立服务器部署不必为了跳转而整体迁入云托管。 |
| 电脑浏览器 | 展示承接茶单的小程序码，由手机扫码继续 | 作为推荐的兼容方案，不承诺所有桌面浏览器都能直接唤起微信。取得品牌接口能力后才生成带茶单标识的小程序码。 |
| 补充入口 | URL Scheme | 可用于部分微信外场景；系统和浏览器的行为不同，不作为唯一入口。明文 Scheme 也需要目标小程序在后台声明允许。 |
| 微信内分享 | Short Link | 可用于微信内打开小程序。官网概述与接口页对开放范围存在不一致，是否可用须以品牌账号实际权限和接入验证为准，不作为本阶段必需能力。 |

URL Link 与开放标签可以传参数；目标小程序必须主动解析参数并实现业务逻辑。开放标签可以跳转合法合规的第三方小程序，这不等于获得对其购物车或订单的写入权限。

## 开发与验证要点

- 所有微信接口凭证和签名生成逻辑只放在服务端。网页只取得可公开使用的跳转结果；不得提交 AppSecret、访问令牌等秘密到仓库。
- 加密 URL Link 当前支持 `path` 与 `query`，也支持追加编码后的 `cq` 参数。优先传短期标识，具体字段与解析方式在接入时联调。
- 链接过期时间与茶单有效期分别管理。即使链接仍可打开，茶单过期也应拒绝还原旧配置并引导重新确认。
- 本项目是单页应用。如使用开放标签，前端路由导致页面 URL 改变后，需要按微信官方要求重新进行对应 URL 的权限配置。
- 验证手机微信内、手机外部浏览器与电脑扫码三类入口；覆盖取消跳转、链接过期、茶单过期、商品售罄、价格变化、选店变化和登录后继续承接。
- 联调成功前，产品文案只描述实际已实现的能力；完成真实衔接后再启用带配置跳转入口。
