# 官方小程序下单衔接

当前版本把选好的商品和期望配置整理成商品卡，并预留官方小程序确认页的衔接接口。**尚未接入品牌官方小程序接口；点击入口不会创建订单、占库存或发起支付。** 有效配置返回“暂未开通”，前端保留配置并展示返回说明；不会拼接或打开猜测的小程序地址。

## 当前接口

`POST /api/order-handoff`，请求为 JSON，类型位于 `shared/contracts.ts` 的 `OfficialOrderDraft`：

```json
{
  "drinkId": "p01",
  "drinkName": "茉莉冷萃水",
  "quantity": 1,
  "storeName": "中华茉莉园店",
  "options": {
    "volume": "按门店规格",
    "sweetness": "按门店默认",
    "temperature": "按门店默认",
    "toppings": "未加料"
  },
  "note": "希望清爽一些"
}
```

- `drinkId` 是本站目录 ID，允许 1～64 个英文字母、数字、下划线或短横线。它不是官方商品或 SKU ID。
- `drinkName` 为必填，`storeName` 可省略；去除首尾空白后均为 1～160 字符。
- `quantity` 必须是 1～20 的整数。
- `options` 四个字段必填：`volume`、`sweetness`、`temperature` 各为 1～80 字符，`toppings` 为 1～300 字符，均去除首尾空白。
- `note` 可省略，最多 500 字符。未提供的门店不能被默认为已经选定或支持下单。
- 顶层和 `options` 均拒绝未声明字段，包括客户端价格、付款金额和跳转地址。

服务端重新读取本地目录，确认商品存在、`available` 为 `true` 且属于 `observed` 或 `managed` 目录。**这只是本地资料校验，不是官方实时库存校验。** 客户端传来的名称、门店名称、容量、甜度、温度和加料都只是期望配置；接口不会据此确认官方支持这些选项，也不会采信客户端报价。

有效请求目前固定返回 HTTP 200：

```json
{
  "status": "unavailable",
  "message": "官方小程序下单暂未开通，这份配置尚未提交。你可以先保存或复制配置。"
}
```

错误沿用 `ApiError`：格式错误为 `400 INVALID_INPUT`（非法 JSON 为 `400 INVALID_JSON`），商品不存在为 `404 DRINK_NOT_FOUND`，本地停售或移出当前目录为 `409 DRINK_UNAVAILABLE`。接口每个来源每分钟最多 30 次，并受全局 API 限流约束。

预留的成功响应类型为 `{ "status": "ready", "url": "官方确认页链接" }`，当前代码不会返回这一分支。前端仅在收到服务端正式生成、验证过的 `ready` 响应后进入官方确认页；`ready` 也不表示已下单或已付款。

## 接入时需要品牌提供

1. 小程序标识、受支持的跳转方式、页面路径与参数约定，以及已授权的开发和测试环境。是否能直接打开预配置确认页，应以品牌提供的能力为准。
2. 正式的门店目录和 `storeId`，官方商品 ID、SKU ID、规格组及选项 ID。本站 `drinkId` 与展示文字必须通过明确映射转换，不能拿名称当商品标识。
3. 可按门店查询的实时在售状态、库存、价格、可选糖冰、小料及选项组合规则。还需约定价格或库存变化时的错误码和刷新方式。
4. 生成官方确认页链接或保存配置草稿的授权接口、凭证、安全校验、有效期与幂等规则。服务端保管凭证，不下发至浏览器。

接入适配器后，服务端应先解析草稿、映射门店与 SKU，再向官方核验规格组合、实时价格和库存。缺少映射、不可售或选项不支持时保留用户配置并提示修改，不自动换商品或减少配置。返回的链接应由官方能力生成并在服务端验证为受信任目标，不接受任意客户端跳转地址。

流程止于**打开官方预配置确认页，由用户核对并确认下单**。本项目不会自动提交付款；若官方只支持打开首页或商品页，应在界面准确说明需要继续选择的内容，不声称配置已带入。无需为了前端演示伪造订单号、支付状态或直达链接。

## 当前验证

`tests/order-handoff.test.ts` 覆盖正常及数量边界、非法输入、未知字段与报价注入、停售和历史目录、伪造商品文字，以及无数据库写入和无外部调用。测试使用临时数据库，不修改本地工作数据，也不调用小程序或消耗模型额度。
